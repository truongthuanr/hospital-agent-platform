# MVP v1.0 — Foundation Checklist

This checklist expands [Stage 0: Foundation](../implementation-checklist-v1.0.md). It prepares the shared infrastructure and contracts needed for the first durable execution. Check an item only when the implementation and its verification evidence exist. Use synthetic identities and hospital data only.

Design references: [System Contract](../../design/system-contract.md), [Workflow Orchestration](../../design/workflow-orchestration.md), [Platform Operations](../../design/platform-operations.md), and [LLD](../../low-level-design.md).

## 1. Project and local runtime

- [x] Create a clear project layout for the API, worker, shared contracts, database access, migrations, and tests. Keep hospital business models outside platform core.
- [x] Set up Python dependency management and separate commands to start the API, start the worker, run migrations, and run checks.
- [x] Add environment-based configuration with validation at startup. Provide an example configuration containing no real secrets or patient data.
- [x] Add Docker Compose services for the API, one worker deployment, and PostgreSQL, with persistent database storage and documented startup commands.
- [x] Ensure API and worker use the same PostgreSQL configuration and do not rely on shared in-memory state.

## 2. Database and migrations

- [x] Set up the database connection and migration framework; create a first migration for foundation-owned tables only.
- [x] Create a fixed synthetic tenant identity for MVP; include `tenant_id` in all tenant-owned foundation records and queries.
- [x] Create the `sessions`, `idempotency_records`, `agent_versions`, and minimal redacted audit storage required by the foundation contracts.
- [x] Define primary keys, tenant-scoped uniqueness, foreign keys, and indexes for these tables; store timestamps as UTC `timestamptz`.
- [x] Make migrations repeatable in a fresh local environment and test applying them from an empty database.

## 3. Shared contracts and API conventions

- [x] Define `ActorContext`, `ExecutionRef`, `StepRef`, `JobRef`, and `OperationRef` with distinct identifiers and explicit ownership of each field.
- [x] Require server-derived actor and tenant context; never accept client-provided tenant/owner fields or model output as authority.
- [ ] Define schema-versioned request/response types and validate data on entry and exit. Reject malformed or unsupported versions.
- [x] Standardize the HTTP error body as `{error_code, message, trace_id, retry_after?, details?}` with safe, redacted details.
- [x] Assign or propagate a `trace_id` on each API request and include it in responses and structured logs.

## 4. Authentication, authorization, and audit

- [x] Issue opaque random sessions for synthetic patients and provisioned demo staff; store only a keyed token hash, tenant, actor type, expiry, and revocation state.
- [x] Resolve a live session on each request. Bind patient sessions to the fixed synthetic tenant and limit patients to their own resources.
- [x] Provide CLI bearer authentication. If a browser flow is included, use secure cookies and a session-bound CSRF token for mutations.
- [x] Keep staff credentials outside the repository and verify staff identity before staff-only actions.
- [x] Implement the centralized policy port with default deny and explicit allow rules for the initial foundation actions; define the actor, tenant, action, resource, state, and pinned-version inputs.
- [x] Record allow and deny decisions with actor, action, resource, outcome, and `trace_id`; redact patient text, tokens, credentials, and unneeded payloads.
- [x] Verify that an expired or revoked session fails and that an unauthorized actor cannot perform a staff-only action.

## 5. HTTP idempotency contract

- [ ] Require an opaque, nonempty `Idempotency-Key` of at most 128 bytes on execution-creation requests; reject malformed keys.
- [x] Define canonical UTF-8 JSON for method, route resource ID, validated body, and requested agent version: sorted keys, compact separators, normalized values, and no non-finite numbers.
- [x] Compute the SHA-256 request hash without timestamps, `trace_id`, or volatile headers.
- [x] Store records under `(tenant_id, operation_type, key)` with request hash, status, result reference, and expiry; define demo retention of at least seven days and longer for active or uncertain runs.
- [x] Specify the API behavior for same key/same payload, same key/different payload (`409`), and an in-progress request. The atomic execution-admission transaction is implemented in Stage 1.

## 6. Immutable agent and workflow registry

- [x] Create `agent_versions` with `(tenant_id, agent_id, version)` identity, immutable published snapshot/hash, and publication time.
- [x] Define a minimal workflow schema with `step_id`, type, input/output schema versions, allowed successors, timeout, and retry policy. Start with `RULE` and `FINAL` steps.
- [x] Validate the graph at publication: reject missing successors, invalid transitions, unbounded loops, and incompatible declared contracts.
- [x] Publish one synthetic agent/workflow version and load it by exact version; reject attempts to edit a published snapshot.
- [x] Define how the published snapshot records version references needed by later prompt, model, policy, tool, and hospital configuration, without building those modules now.

## Foundation exit gate

- [ ] Docker Compose starts the API, singleton worker, and PostgreSQL from a clean checkout using documented commands.
- [x] The migration applies to an empty database and reruns without altering existing data.
- [x] Health/readiness checks reflect basic process and database availability; logs and responses carry a `trace_id` without exposing secrets or raw patient text.
- [x] A synthetic patient and demo staff member can authenticate; expired/revoked sessions and denied policy actions are rejected and audited.
- [x] Valid and invalid idempotency keys, canonical request hashes, and same-key/different-payload conflicts have focused contract checks.
- [x] A valid workflow version can be published and loaded; invalid or modified published versions are rejected.

**Next stage:** [Durable execution](../implementation-checklist-v1.0.md) adds execution/checkpoint/event/job tables, atomic `202` admission, CAS transitions, worker claims, waiting, retries, and restart recovery. LLM, MCP, Memory, RAG, pgvector, and hospital-specific schemas are outside this foundation stage.

## Verification and remaining work

- Verified with `python -m pytest -q` (4 passed), `alembic upgrade head` on an empty PostgreSQL database, a second migration run, `alembic check`, repeated synthetic seed runs, and live API smoke requests for health, patient/staff sessions, policy denial, publication, and duplicate-version conflict.
- The execution-creation endpoint and its mandatory `Idempotency-Key` are part of Stage 1 admission. The foundation provides the validation dependency, canonical hash, storage model, and conflict handling contract.
- The registry payload is schema-versioned and rejects unsupported versions. Remaining API request and response models need an explicit schema-version convention before this checklist item is complete.
- The standard Dockerfile build needs access to the Python package index. In this environment Docker could not resolve the index, so the services were verified using an offline image built from Python 3.12 wheels. A clean-checkout online build remains unverified.
