# MVP v1.0 — Durable Execution Checklist

This checklist expands [Stage 1: Durable execution](../implementation-checklist-v1.0.md). Complete it as runnable slices, from atomic admission through a restartable `RULE → WAIT_INPUT/WAIT_APPROVAL → FINAL` workflow. Check an item only when its migration, code, and verification evidence exist. Use synthetic identities and data only.

Design references: [System Contract](../../design/system-contract.md), [Agent Runtime](../../design/agent-runtime.md), [Workflow Orchestration](../../design/workflow-orchestration.md), and [ADRs 001–004](../../adr/README.md). Stage 0 already supplies sessions, policy, idempotency hashing/storage, and an immutable `RULE`/`FINAL` registry; extend those contracts instead of duplicating them. LLM, MCP, Memory, RAG, hospital business tables, multi-worker leases, and cancellation belong to later stages.

## 1. Contracts and migration

- [x] Define versioned API request/response models for create, execution reads, event pages, input, and approval; reject unsupported schema versions and unknown fields. Complete the open Stage 0 schema-version item.
- [ ] Extend the published workflow schema with `WAIT_INPUT` and `WAIT_APPROVAL`, their input/decision schemas, allowed successors, and rejection branches. Reject missing successors, invalid contracts, and unbounded loops at publication. Publish a new version; do not alter existing snapshots.
- [ ] Define a typed `StepDecision` and explicit transition table. Validate the decision against the pinned graph and current state before a database write. Keep step handlers deterministic for this stage.
- [ ] Add an Alembic migration and ORM models for `executions`, `checkpoints`, `execution_events`, `step_attempts`, `input_requests`, `approvals`, and `durable_jobs`. Include the pinned agent snapshot identity/hash and version references, owner session, status, current step, version, trace ID, and timestamps on executions.
- [ ] Add `tenant_id` to every owned row and tenant-scoped foreign-key path. Enforce `executions.version >= 0`, checkpoint `(execution_id, version)` uniqueness, event `(execution_id, sequence)` uniqueness, attempt `(execution_id, step_id, attempt_no)` uniqueness, request `(execution_id, execution_version)` uniqueness, approval `(tenant_id, decision_id)` uniqueness, and job `(execution_id, expected_version, step_id, attempt_no)` uniqueness.
- [ ] Create a partial `(due_at, id)` index for `durable_jobs` in `READY` state and indexes for tenant-scoped execution/event reads. Use UUIDs and UTC `timestamptz`; use database time for expiry and due-time comparisons.
- [ ] Keep checkpoint JSON minimal and schema-versioned: workflow step, references, pending request ID, retry count/due time, and future operation IDs. Exclude raw patient text, secrets, and full conversation history. Add a reader/upcaster boundary for later checkpoint schema versions.
- [ ] Verify the migration on an empty database and against the Stage 0 database; confirm constraints reject duplicate or cross-tenant references. Record the migration command and result.

## 2. Atomic execution admission

- [ ] Add `POST /agents/{agent_id}/executions` with authenticated actor, mandatory validated `Idempotency-Key`, optional published version, and validated initial input. Resolve the requested/current published version once and pin its exact immutable snapshot and references. Reject missing or corrupt snapshots; never fall forward to a newer version.
- [ ] In one PostgreSQL transaction, insert or lock `(tenant_id, operation_type, key)`, compare the canonical request hash, and insert the version-0 `PENDING` execution, checkpoint, first redacted event, and one `READY` start job. Store the result reference in the idempotency row before commit. Make concurrent same-key requests converge on one execution.
- [ ] Return `202` only after commit, including execution ID, status, version, and trace ID. Same key and canonical payload returns the same logical execution; changed payload returns `409`. Define an explicit response for a genuinely in-progress idempotency row rather than creating another execution.
- [ ] Preserve the idempotency row for at least seven days and longer while its execution is active or uncertain. Test lost HTTP response after commit by repeating the request and confirming one execution, one initial job, and one logical result.

## 3. Runtime transitions and CAS

- [ ] Implement `load_execution` and `commit_decision` as runtime ports. Scope every lookup by tenant; reload the pinned workflow and verify its identity/hash before dispatch. A missing pinned snapshot fails safely.
- [ ] Model `PENDING → RUNNING` as a committed start transition with its own checkpoint/event and a successor job at the new version. Model `RETRY_SCHEDULED → RUNNING` similarly when the persisted due time arrives. Document which job and execution version each transition consumes and produces.
- [ ] For each step decision, perform `UPDATE executions ... WHERE tenant_id = ? AND id = ? AND version = expected_version`. In the same transaction, finalize the current attempt/job, insert exactly one checkpoint and ordered redacted event for the new version, and insert the successor job, waiting request, or terminal result.
- [ ] Reject a decision for the wrong current step, job, attempt number, tenant, state, or graph edge. Allocate event sequence while holding the execution row lock; do not leave a completed job without its next durable work intent.
- [ ] On zero-row CAS, roll back the whole decision, reload, and discard stale work. Verify two competing transitions from one version yield one committed version/event/checkpoint path. Treat `COMPLETED` and `FAILED` as terminal.
- [ ] Persist attempt start/end, status, error class, and retry number without exposing input text. Define how a failed transaction or process crash leaves a claimed attempt recoverable and how the next claim avoids a duplicate committed attempt.

## 4. Singleton worker and recovery

- [ ] Replace the Stage 0 worker heartbeat loop with one deployment holding a dedicated PostgreSQL advisory-lock connection for leadership. Do not claim jobs unless that connection still holds the lock; worker readiness reflects leadership. Stop new claims on shutdown.
- [ ] In a short claim transaction, select the oldest `READY` job where `due_at <= database_now` using `FOR UPDATE SKIP LOCKED`, then mark it `RUNNING` with `claimed_at`. Keep handler execution outside the claim transaction.
- [ ] Before dispatch, reload tenant, execution state/version/current step, pinned snapshot, and job identity. Mark stale or already-consumed jobs complete without running a handler. Enforce the policy boundary for worker actions.
- [ ] Commit job completion and successor work through runtime's transition transaction. Catch handler/supervisor exceptions and durably classify the job for retry or failure; do not strand it in memory.
- [ ] After leadership is acquired on startup, return abandoned `RUNNING` jobs to `READY` for revalidation. Preserve each job's persisted due time. This recovery rule applies only to the v1.0 singleton profile; multi-worker leases/fencing are v1.1 work.
- [ ] Verify crash after admission commit, crash after claim, and restart while waiting. Each acknowledged execution must remain discoverable and reach a declared waiting or terminal state after recovery.

## 5. Waiting, input, and approval

- [ ] For `WAIT_INPUT`/`WAIT_APPROVAL`, commit `WAITING_INPUT`/`WAITING_APPROVAL`, the checkpoint/event, and one request record before exposing the prompt. Store only a keyed hash of a cryptographically random one-time input token; record expiry and consumed event/payload hash.
- [ ] Define a recoverable, authenticated way for the owner to obtain or reissue a pending input token if the response carrying it is lost. Token reissue must invalidate the old token and must not resume the execution. Do not put raw tokens in events, logs, or checkpoints.
- [ ] Implement `POST /executions/{id}/input`: verify owner, tenant, policy, current waiting state/version, request ID, token, expiry, and answer schema. In one transaction consume the request, record the input event identity/hash, transition to `RUNNING`, and enqueue a resume job. The worker is free while waiting.
- [ ] Implement `POST /executions/{id}/approval`: require authorized staff and action scope; verify tenant, approval ID, state/version, and decision schema. Store decision ID, actor, decision, audit entry, transition, and resume job atomically. Rejection follows the pinned workflow branch.
- [ ] Return the original logical result for an identical repeated input event ID or decision ID; return `409` for the same ID with changed payload or a stale version. Test duplicate and concurrent submissions, expired tokens, wrong owner, and unauthorized staff.

## 6. Bounded retries

- [ ] Classify timeouts, transport failures, rate limits, and selected 5xx as transient; validation, policy denial, bad permissions, and unsafe decisions as permanent. `RULE`/`FINAL` demo handlers must be deterministic and effect-free.
- [ ] Enforce the pinned per-step attempt budget, including the first attempt. For transient errors with budget remaining, persist the chosen exponential backoff `due_at` (demo default: 1 s base, 30 s cap, ±20% jitter; honor a larger valid `Retry-After`) and a `RETRY_SCHEDULED` transition/job in the same transaction.
- [ ] Mark exhausted known non-effect work `FAILED` with a redacted reason. Never run a retry before its persisted `due_at`, including after restart or clock-independent worker polling.
- [ ] Keep the `RECONCILIATION_REQUIRED` state in the runtime contract, but defer effect preparation, operation lookup, and effect retry to Stage 3. Do not claim a booking fault test is covered by this stage.

## 7. Read APIs, visibility, and evidence

- [ ] Implement `GET /executions/{id}` with redacted status, current step, version, pinned version identity, and timestamps. Implement `GET /executions/{id}/events` with stable ascending sequence, cursor, bounded limit, and redacted payloads.
- [ ] Apply session-derived tenant and owner/staff scope to every read and mutation. Return `404` for absent or foreign-tenant IDs, `403` for known same-tenant resources outside scope, `409` for state/version/idempotency conflicts, and `422` for schema-invalid content. Audit allow/deny without patient text or tokens.
- [ ] Propagate `trace_id`, execution ID, and job ID through API, runtime, and worker logs/events without logging raw answers, credentials, or unredacted payloads.
- [ ] Add integration checks for the full `RULE → WAIT_INPUT → FINAL` and `RULE → WAIT_APPROVAL → FINAL` paths, including rejection. Publish a newer agent version while an older execution waits; resume must use the older pinned graph and references.
- [ ] Run the fault matrix against PostgreSQL: lost response after commit, kill after claim, concurrent CAS, duplicate input/approval, restart before retry due time, stale job, and unauthorized/foreign access. Record commands, fixture/version IDs, observed state/version/event/job counts, and pass/fail results.

## Stage 1 exit gate

- [ ] API and singleton worker complete both demo workflows through PostgreSQL with no in-memory progress dependency and no lost acknowledged execution in the recorded crash/restart suite.
- [ ] One execution version has at most one committed transition; every nonterminal runnable transition has a durable next job, and every waiting transition has a durable pending request.
- [ ] Retries honor persisted due times; waiting releases the worker; an existing execution remains on its pinned published version after a newer publication.
- [ ] All required API visibility, duplicate handling, and error responses are covered by evidence. Link the evidence here before checking this gate.
